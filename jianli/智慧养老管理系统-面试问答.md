## 一、项目与模块总览

### Q1. 简单介绍一下你的项目
> 我独立完成了一个面向养老院的"智慧养老管理系统",前后端分离。
后端 Spring Boot 3 + MyBatis-Plus + MySQL,负责老人档案、护理计划→任务执行、体检预约与结果记录、RBAC 权限管理;前端有两个:后台管理端 Vue3+Element Plus(ui-admin 的重构版 ui-admin_2),老人/家属 H5 端 Vue3+Vant(ui-app)。
最近还做了两件加分事:①给后台首页做了基于聚合 SQL 的数据可视化看板;②给老人端接入阿里云百炼大模型,做了"康养小智"AI 健康助手,会结合老人在系统里的健康档案回答。
数据库共 18 张表,覆盖权限、老人、护理、体检四大模块。

### Q2. 系统有哪些模块?逐个介绍 ⭐
1. **登录/鉴权**:两套入口——员工后台 `/admin/users/login`、老人端 `/app/elders/login`,各自签 JWT,LoginInterceptor 统一拦 `/**(除登录)`,前端 axios 拦截器带 token、遇 401 跳登录。
2. **老人档案 + 标签**:elder 基本信息(身份证/生日/状态0禁用~5已退住)与 tag 多对多,用于筛选、慢病标记。
3. **护理管理**(核心闭环):
   - 护理等级(自理/半护理/全护理)、护理项目(价格/图片/要求)——基础字典;
   - 护理计划 care_plan + 明细 care_plan_item(哪天几点做哪个项目、周期天/周/月、频次),关联老人、护理员、等级;
   - 护理任务 care_task:保存计划时按明细生成"待执行任务",护理员执行后填状态/实际时间/结果/打卡照片。
4. **体检模块**:exam_item(项目含参考范围、数值/文本型)、exam_package(套餐)+套餐-项目多对多;exam_appointment(老人预约/体检单)+ exam_appointment_item(每项结果、异常标记)。
5. **RBAC 权限**:user/role/permission(目录-菜单-按钮树)/user_role/role_permission;登录后返回菜单树与按钮码。
6. **后台首页可视化**:6 张统计卡 + 4 张 ECharts 图(老人状态/年龄/护理计划等级分布、任务完成率近7天趋势),数据来自统计接口。
7. **老人端 H5**:首页、体检套餐选购、预约、我的预约、个人中心、康养小智 AI 助手。
8. **辅助能力**:阿里云 OSS 图片上传、EasyExcel 用户表导入导出。

【真实边界】移动端首页的"今日健康数据/公告"目前是 mock 数据,还没接真实接口——如果被问到,如实说,并说下一步计划用 AI/护理记录去填充。

### Q3. 项目里最难/最有含金量的点是什么?(自己选 2~3 个)
- 护理计划"头表+明细+生成任务"的**事务级联**,以及改计划时"只重建待执行任务、保留打卡历史"的语义。
- **动态权限**:permission 自关联树,登录后按角色聚合出菜单+按钮码。
- **快照设计**:任务冗余项目名、体检明细冗余名称/价格,防止字典改名毁历史。
- 近期的 **AI 助手 + 健康上下文 + 医疗安全人设**。
- 统计看板:纯 SQL 聚合 + Service 补零补日期,一次接口出 4 图数据。

## 二、库表设计(最可能被深挖)

### Q4. 库表是怎么设计的?讲讲你的设计过程 ⭐
> 我是"先业务流程、再模块拆表、最后定字段与约束"：
1. **业务角色梳理**:员工(管理员/护工)、老人/家属 → 老人与员工是两类主体(user、elder 分开)。
2. **按模块拆实体,再拆关联**:
   - 权限要通用 → RBAC 五表:主体 user、客体 permission(目录/菜单/按钮自关联树),user-role、role-permission 两张中间表,把"谁有什么权限"完全解耦;
   - 老人要打标签 → elder、tag、elder_tag 中间表(多对多);
   - 护理是"配置-计划-执行"三段:等级/项目是字典;计划是头;同一计划含多个护理项目明细 → care_plan + care_plan_item 一对多;执行层面按天生成 care_task;
   - 体检是"字典(项目/套餐+组合关系)-预约单-结果明细":套餐和项目多对多用 exam_package_item;一次预约一个套餐,结果一行一项目 → exam_appointment + exam_appointment_item 一对多。
3. **字段层面定规范**:主键 bigint 自增;金额 decimal(10,2);状态用 tinyint 并用 COMMENT 写清楚每个取值含义;记录 create_time/update_time;需要软删的主表加 deleted;对唯一业务键建唯一索引(name/code)。
4. **做权衡**:
   - 不加物理外键,由 Service 层保证级联(软删除场景下外键反而麻烦);
   - 关键历史字段做"冗余快照"(项目名、价格),改名不影响历史;
   - 单表记录"快照价格+套餐id",套餐以后调价不影响已预约记录。

### Q5. 为什么不用外键?
> ①本项目走 MyBatis-Plus 逻辑删除,外键+软删组合很别扭;
②删除/更新靠 Service 显式级联(如删护理计划同时删明细和任务),逻辑清晰、可控;
③性能上避免每次写操作的约束检查。代价是"应用层必须写对",所以我把关键级联都加了 @Transactional 兜底。
(加分句:如果是财务/订单强一致场景我会选物理外键或数据库约束,这里是业务中间态多,选应用层。)

### Q6. 逻辑删除怎么实现?有没有坑?
> MyBatis-Plus 全局配置 logic-delete-field + 实体 @TableLogic,BaseMapper 的增删查会自动带 deleted 条件。
坑:①**自己写的 SQL(注解或 XML)不会自动拼 deleted**,比如 PermissionMapper.xml 的 JOIN 就要手动加 p.deleted=0,否则可能查出已删数据(我已在改进清单里);②唯一索引与逻辑删除冲突——同名软删后再建会撞唯一键,一般方案:唯一键带 deleted 或存 deleted_at 时间戳。

### Q7. permission 一张表怎么同时做"菜单"和"权限"?
> 用 type 区分:0=目录(可含子菜单,无路由)、1=菜单(有 path,与前端路由对应)、2=按钮(permission_value 存 user:add 这类码,无 path/icon 也可)。
parent_id 自关联建树(父 0 为顶级)。查询时:登录用户 → user_role→role_permission→permission 三表 JOIN,type=0/1 的用 buildTree 递归拼菜单树给前端渲染,type=2 的收集成按钮码集合 btnList,前端按钮用 `hasBtnPermission('user:add')` 控制。
【真实边界】当前按钮码(type=2)种子数据还没有配全,前端做了"btnList 为空则放行"的兼容;且真正防越权还需要接口侧校验(见改进)。

### Q8. 如果要新加一个"床位/房间管理",你会怎么设计? ⭐(考设计能力)
> 我会按同一套路:
- 表:`floor/building`(可选)或直接 `room`(房间:编号、楼层、类型、性别限制、状态)、`bed`(床位:room_id、床号、状态0空闲1占用2维修);入住表 elder 增加 bed_id 或在 elder 上加字段,退住时释放;
- 唯一约束:同房间床位号唯一;床位状态与 elder.status 联动(入住中→占床,退住→释放,事务内完成);
- 统计:入住率 = 占用床位数/总床位数,JOIN 后 group by 房间/楼层 → 又喂给 ECharts。
这样讲,面试官看到你"会从业务出发抽象表并考虑约束与统计"。

### Q9. 为什么要"冗余快照"?举个例子
> 例:care_task 里冗余 care_item_name,而不是只存 care_item_id。
原因:护理任务记录的是"某天实际做了什么",是历史事实。如果只存 id,护理项目以后改名或删除,历史任务显示就错/空。体检明细 exam_appointment_item 冗余 item_name、appointment 冗余套餐价同理(套餐调价不影响历史单金额)。

## 三、认证与权限

### Q10. 登录与鉴权流程讲一下(JWT)⭐
> 登录:按 name 查用户(老人端查 elder),比对密码,查状态;成功用 java-jwt 签发 token,载荷放 {id, name}。
之后每个请求:前端 axios 请求拦截器在 Header 加 Authorization;后端 LoginInterceptor 拦 /**(WebConfig 注册,放行两个登录接口),验签失败直接返回 401;前端响应拦截器收到 401 跳登录。
Controller 里需要当前用户时再 JwtUtil.parseToken 取 id(如 userInfo、resetPassword、AI 对话取老人 id)。

### Q11. 为什么用 JWT 不用 Session?token 过期怎么办?
> 优点:无状态,适合前后端分离/多端(后台+H5),服务端不存会话,扩容友好。
过期:JwtUtil 解析带过期校验,失败即 401 → 前端引导重新登录。
【真实边界】当前没做 refresh_token、也没有登出黑名单(removeToken 只是前端删)。改进方向:token 7 天不过期可加短期 access + 长期 refresh;要主动踢人可引入 Redis 黑名单/会话版本号。

### Q12. 你这个权限是"真权限"吗?会不会越权?⭐(高频陷阱题)
> 诚实回答:我做的是**菜单/按钮层面的权限**(按角色控制"看得见/点得动"),这是 RBAC 的第一层。
但它还不是**接口级权限**:后端目前只校验"登录没登录",没有校验"这个角色能不能调这个接口"。如果知道 URL,理论上可以直接调。
我的改进方案(已在做计划):接口/操作绑定 permission_value(如 user:add),用自定义注解 + AOP 或拦截器,在调用前查当前用户角色是否有该权限码,没有返回 403。另外把当前登录用户放 ThreadLocal,统一取 id,避免每处手动解析 token。

### Q13. 老人端 token 和员工端 token 会串吗?
> 都走同一套 JwtUtil/LoginInterceptor,但登录查询对象不同(员工查 user,老人查 elder),token 载荷都是 {id,name}。风险是"同一个 token 在两端都能过拦截器",真正要区分可以在载荷加 type 字段,接口侧校验 type(比如 /app/** 只允许 elder 类型),这是我列的改进项之一。

## 四、MyBatis-Plus / SQL / 事务

### Q14. 分页是怎么实现的?
> 后端注册 MybatisPlusInterceptor + PaginationInnerInterceptor(DbType.MYSQL);列表接口 Page<>(page,limit)+ selectPage。原理:MP 分页插件拦截 SQL,自动生成 COUNT 查询和 LIMIT 语句。
条件用 LambdaQueryWrapper:like/eq/between 前加 `!ObjectUtils.isEmpty(x)` 做条件开关,不传就不拼;orderByDesc 按创建时间倒序。

### Q15. 列表要显示"老人名/护理员名/等级名",怎么避免 N+1?⭐
> 两种做法我项目里都有:
- 简单页(如护理任务列表)在 SQL/VO 阶段拼好,或查回后循环补;
- 批量做法(护理计划列表):先 selectBatchIds 一次性查出本页涉及的所有 elder/user/careLevel,用 stream 收集成 Map<id,name>,再回填到 VO —— 把"N 次单查"变成"3 次批量查"。
(补一句:N+1 排查——看到循环里查库就要警觉;也可用 MyBatis 日志 StdOutImpl 观察 SQL 条数。)

### Q16. 自定义 SQL 和 MyBatis-Plus 怎么共存?
> BaseMapper 管单表 CRUD/分页;复杂 JOIN(权限三表)写在同名 XML(方法声明在接口,SQL 在 resources/mapper/*.xml);纯聚合(统计)用 @Select 注解。三种写法按复杂度选用。
注意点:自定义 SQL 不自动带逻辑删除与自动填充,需要时手动补(前面 Q6 讲过)。

### Q17. @Transactional 用到哪些场景?自调用会不会失效?⭐
> 用到:护理计划 add/update/removeById(头+明细+任务级联)、角色/标签"先删后插"分配等写多表场景。
注意:①@Transactional 默认只回滚 RuntimeException,业务上建议注明 rollbackFor 或统一抛 ServiceException(它继承 RuntimeException);②同类内自调用(this.add())会绕过代理导致事务失效——我习惯把事务方法放到可被代理调用的边界,必要时拆 Service。
(面试加分:能主动说出"自调用失效、代理机制"说明真写过。)

### Q18. 有没有遇到过并发问题?怎么防?
> 诚实:当前项目单机演示为主,写操作基本靠"先删后插+事务",没专门做并发控制。
如果要防(如:护工重复提交完成任务、退住并发),方案:①乐观锁,实体加 @Version,update 条件带版本号,失败重试/提示;②状态机校验,更新 SQL 里带 `WHERE status=待执行`,受影响行数为 0 说明已被处理,提示"该任务已处理"。
这样回答:既承认现状,又给出方案,显得有意识。

### Q19. 统计接口(可视化)怎么写的?
> 后端 StatsMapper 写聚合 SQL,如老人年龄分布用 `CASE WHEN TIMESTAMPDIFF(YEAR,birthday,CURDATE())<60 THEN 0 …END` 分桶 + GROUP BY;任务趋势按 plan_execute_date BETWEEN 近7天 GROUP BY,用 SUM(status=1) 算已完成。
Service 做两件事:①对"今天没有任务"的日期补 0、把 6 个状态桶补全,保证折线/饼图坐标完整;②算完成率并返回一次 JSON 给前端,前端 ECharts 直接 setOption。这样数据库只查一遍、接口一次返回 4 组图数据。

## 五、AI 助手模块

### Q20. AI 助手怎么实现的?⭐
> 老人端点"康养小智"→ 聊天页把历史消息(不含欢迎语、限制 12 条/每条≤2000 字)POST 到 `/app/ai/chat`。
后端从老人 token 取 elderId,然后:
1. 只读组装"该老人健康档案摘要"(基本信息/标签=慢病/进行中的护理计划与等级/最近 8 条护理任务结果/最近 2 次已完成体检的异常项)——**服务端拼好塞进 system**,模型就能基于真实数据回答;
2. system = 医疗安全人设(kangyang-xiaozhi-system.md):不替代医生、紧急情况固定话术、禁止虚构"已通知家属"等;
3. 用 JDK HttpClient 以 OpenAI 兼容协议调阿里云百炼 compatible-mode(v1)/chat/completions,model 用配置的 qwen-plus,key 从 application.yml 的 spring.ai.dashscope 读取(不进代码)。
> 交互上是"前端传历史、后端无状态",天然适合多端;后续要体验更流畅可改 SSE 流式。

### Q21. AI 的安全边界怎么做的?(很有深度的问题)
> 三层:
1. 提示词层:明确角色不是医生、不做诊断处方、紧急模式用固定清晰话术、区分"可以申请"与"已成功完成";
2. 输入输出层:角色白名单(只收 user/assistant)、长度与条数上限、只查自己 elderId 的数据、返回内容非空校验;
3. 工程边界:v1 没有工具调用,所以 AI 只能说"可以联系/建议",不能说"已经通知",避免虚假承诺;真做工具(提醒/呼叫)时必须用户授权 + 工具执行成功回执后,才允许宣称完成。
(还能补一句隐私:绝不索要验证码/支付密码,不进对话的是身份证号/密码等敏感字段。)

### Q22. 为什么没用 spring-ai 的 ChatClient/ChatModel,而是自己 HttpClient?
> 项目引入的是 spring-ai-alibaba starter 以复用其配置(spring.ai.dashscope),但各版本 ChatModel API 有差异、为控制风险与依赖,我直接用配置值 + 标准 OpenAI 兼容协议手写 HTTP 调用,行为完全可控、便于阅读。如果要流式,再基于同一协议接 SSE。这是可以坦诚讲的工程取舍。

## 六、前端相关(顺带)

### Q23. 前后端怎么联调/跨域?
> Vite dev server 配 proxy:`/api` → `http://localhost:8081` 并 rewrite 掉 /api;前端只发相对路径 /api/xxx,开发无跨域;生产由同域网关/nginx 反代。两种角色各一个 base:后台 `/api/admin`、老人端 `/api/app`。

### Q24. 你做了哪些性能/工程优化?
> 后台:路由懒加载,各页面独立 chunk(主包 1308KB→1199KB);Element Plus 全量引入可再按需(改进项);弹窗内容超高滚动、空态/加载态。
后端:列表批量回填防 N+1、聚合统计一次接口、懒加载不涉及。
另外构建保持 npm run build 零错误,分层规范便于扩展。

## 七、场景 & 压轴题

### Q25. 如果老人档案有 10 万条,列表接口怎么优化?

5) 上传的头像走 CDN。
